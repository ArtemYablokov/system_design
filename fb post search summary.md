# Конспект: System Design — поиск по постам Facebook

Итоговый разбор беседы (Jun 16–17). Тема: дизайн сервиса полнотекстового поиска по постам с ранжированием по лайкам. Ниже — все ключевые развилки, вопросы и выводы по порядку нарастания темы. Схему см. в начале чата.

## 0. Исходный дизайн и два открытых вопроса

Скелет, который ты принёс, оценён как корректный:
- inverted index: `keyword → list of post ids`
- асинхронное извлечение ключевых слов через очередь (write server → queue → parse server → Index DB)
- Kinesis как поток лайков (like server → Kinesis → worker → Likes DB + кэш)
- CDN для текста/картинок + read replicas для Post/Likes DB

Два вопроса, на которые ты не мог ответить:
1. **Как хранить топ-лайкнутые посты**, если лайки динамические (в отличие от таймстемпов, где для топ-1000 хватает просто упорядоченного списка).
2. **Как обрабатывать поиск по двум словам** (твоя идея: 2-pointer merge отсортированных списков на сервере + популярные би-граммы как ключ).

## 1. Главная развилка, которой не было на схеме: как шардируется Index DB

Это вопрос, на котором интервьюер давит в первую очередь. Два варианта:

- **Term-partitioned** (каждому ключевому слову — свой шард, на нём весь его posting list): поиск по одному слову — это один хоп; поиск по нескольким словам требует тащить списки с разных шардов и мерджить на сервере — это и есть твой ответ про 2-pointer.
- **Document-partitioned** (каждый шард держит срез постов, делаем scatter-gather): мердж происходит на каждом шарде, потом собираем top-K.

Твой ответ про merge неявно предполагает **term-partitioned**. Это нужно проговаривать вслух.

**Ключевая деталь:** posting lists отсортированы по `postId = userId + tmstmp`. Именно это делает 2-pointer merge возможным и бесплатно даёт сортировку по свежести (recency). `postId` и `tmstmp` — одна и та же ось сортировки, потому что таймстемп зашит внутрь id.

## 2. Q2a — топ-лайкнутые посты при динамических лайках (главная проблема)

**Суть проблемы:** нельзя держать posting list отсортированным по лайкам так же, как по таймстемпу. Таймстемпы неизменны (новый пост → в голову списка, порядок сохраняется), а лайки мутируют постоянно.

**Вывод — разделить структуры (decouple ordering from posting list):**
- Основной posting list держим отсортированным по `postId` — для merge и recency.
- Отдельная структура `keyword → top-K`, обновляемая **асинхронно из потока Kinesis, не на write-пути**.

**Два контроля стоимости** (наивный fan-out «каждый лайк → обновить структуру для всех keyword этого поста» дорог):
- Держать top-K структуры только для **горячих keyword** (доступ скошен — это уже доказывает твой LFU-кэш). Длинный хвост — сортируем маленький результат на лету в момент запроса.
- **Батчить дельты лайков** в воркере и применять периодически. Ранжирование по лайкам может отставать на секунды — для поиска приблизительный top-K нормален.

### Что за структура для top-K по лайкам

Это **TreeMap / sorted set**, где на каждом обновлении: удалить запись (log N) → обновить ключ → вставить обратно (log N). Итого **2 log N на обновление**. Эту цену платит любая структура, упорядоченная по мутирующему значению (TreeMap, Redis ZSET на skiplist, heap).

**Важное уточнение:** простой `TreeMap<likeCount, postId>` ломается, потому что:
- лайк-каунты коллизятся (много постов с одинаковым числом),
- нельзя найти текущую запись поста, не зная его старый score.

Поэтому на практике — **две структуры**:
- `HashMap<postId, likeCount>` — найти текущий score за O(1) (чтобы знать, что удалять);
- `TreeMap` / sorted set по ключу `(likeCount, postId)` — собственно порядок и чтение top-K.

Обновление = взять старый score из хэшмапы (O(1)) → удалить `(oldScore, postId)` из дерева (log N) → записать новый score в хэшмапу → вставить `(newScore, postId)` (log N).

> Эта пара «хэшмапа + skiplist» — буквально то, чем **Redis ZSET** является внутри. ZSET = sorted set: коллекция, где у каждого члена числовой score, поддерживается порядок по score, «дай top-1000 по score» — дешёвая встроенная операция. Вспомогательная мапа — то, что делает шаг «удалить старую запись» возможным без скана.

### Проблема корректности top-K (эвикция / cutoff)

Лайки поста растут, поэтому пост, которого нет в top-1K сегодня, может войти завтра. Если хранить только текущий top-1K — не поймёшь, когда #1001 обгонит #1000 (ты его выбросил). Два выхода:
- **Threshold + recompute:** хранить top-1K + лайк-каунт 1000-го (cutoff). Из потока Kinesis: когда пост пересекает cutoff — вставить, выбросить минимум. Периодически пересчитывать из полных данных для коррекции дрейфа. Приблизительно, дёшево.
- **Хранить больше, чем отдаём:** трекать top-N, где N ≫ 1K (например top-10K), чтобы движение происходило внутри отслеживаемого множества и полный пересчёт нужен редко.

В любом случае апдейт идёт асинхронно из потока лайков, батчами, никогда не на read-пути.

## 3. Q2b — поиск по двум словам

Твой ответ верный и покрывает два разных запроса:
- **AND (оба слова присутствуют)** → 2-pointer пересечение двух отсортированных списков, O(n+m), т.к. оба отсортированы по `postId`. Ускорение — **skip pointers** в posting lists, чтобы перепрыгивать по более длинному списку, а не сканировать целиком (стандартный приём).
- **Фраза ("w1 w2" подряд)** → это и обрабатывают твои «популярные би-граммы как ключ»: предпосчитанный posting list для пары. Но только для **топ-частотных** би-грамм — все пары дают комбинаторный взрыв. Общий fallback — **positional index** (хранить позиции термов в posting list, проверять смежность после пересечения).

**Связь с Q2a:** 2-pointer merge работает только потому, что у обоих списков общий ключ сортировки (`postId`). По лайкам так мерджить нельзя. Паттерн: **пересечь по postId → взять результат → отранжировать по лайкам (look up score / ZSET) → вернуть top-K**. Не мерджить по динамическому ключу.

> Нюанс: если хранить отдельный posting list, уже отсортированный по `likeCount`, то два таких списка мерджатся нормально — `postId` просто разрешает ничьи. Проблема не в mergeability, а в **поддержке**: лайки мутируют, держать список отсортированным = пересортировка на каждый лайк. Поэтому это и живёт в ZSET, обновляемом из Kinesis.

## 4. Index DB на Dynamo: модель PK/SK и две ловушки

Твоя мысль: шардировать по keyword, чтобы взять managed KV-стор (Dynamo и пр.) вместо «велосипеда». Это легитимно — managed KV даёт репликацию, failover и решардинг бесплатно. Но у term-partitioning на Dynamo есть чистая часть и две ловушки.

**Чистая часть — модель данных:** не хранить posting list одним blob-значением. Моделировать как `PK = keyword, SK = postId`. Тогда `Query(PK=keyword)` возвращает posting list, уже отсортированный по `postId` (Dynamo сортирует по sort key) — ровно то, что нужно для 2-pointer merge. Recency-сортировка бесплатно, каждая запись posting list — отдельный item.

**Ловушка 1 — размер item:** Dynamo ограничивает item в **400KB**. У популярного keyword («covid», имя знаменитости) — миллионы post id, в один item не влезет. Модель PK/SK это обходит (каждая запись — отдельный item). Если бы хранил одним `keyword→list`-значением — пришлось бы шардировать внутри keyword, и аккуратная абстракция рушится.

**Ловушка 2 — hot partitions** (реальная цена term-partitioning, Dynamo от неё НЕ спасает): все items с одним PK живут на одной партиции, у Dynamo потолок пропускной способности на партицию **~3000 RCU**. Самый горячий keyword в данных = самый горячий по трафику → term-partitioning концентрирует нагрузку именно там, где её больше всего. Adaptive capacity смягчает, но не убирает потолок одного горячего ключа. LFU-кэш спереди многое поглощает; для самых горячих — split posting list по синтетическим PK (`covid#0`, `covid#1`, …) и scatter-read.

**Независимо от Dynamo:** multi-word AND гонит огромные списки по сети. `covid` (50M) ∩ `vaccine` (30M) = тащить оба списка на один сервер для пересечения. Document-partitioning пересекал бы локально на каждом шарде. Это размен эффективности на операционную простоту — проговаривать в интервью явно.

**Важная коррекция (ты сначала думал, что SK скаттерит):** SK **НЕ** скаттерит. Все items с одним PK — на одной партиции, отсортированы по SK. SK даёт **порядок внутри партиции**, а не распределение. Только **salting PK** реально скаттерит. Два разных лимита: item-size (решается PK/SK) vs partition-throughput (решается только salting'ом).

**Твой сильнейший аргумент:** если результаты не скроллятся дальше ~1K (нет других фильтров → 1K даже не пролистать в UI), то полный список из 50M никогда не нужно материализовать. Нужен top-K по релевантности/лайкам, а не весь posting list. Это **ослабляет худшую ловушку** term-partitioning: проблема «covid ∩ vaccine гонит 50M id» в основном испаряется, если всегда ранжируешь ограниченный candidate set.

**Строчка для интервью:** «Принимаю hot-keyword skew и стоимость cross-node merge в обмен на то, что не строю свой шардированный индекс; вот как кэш и PK-splitting ограничивают skew».

## 5. Проблема горячего ключа (hot key) и её митигации

Это **именно проблема single-leader-per-partition** (есть у Dynamo, у другого дизайна может не быть).

**Полный список митигаций:**
1. **Replica** — лечит горячие **чтения** (размазать чтения по копиям). Не помогает горячим записям, но поиск read-heavy → это даёт многое. Дёшево, read-only.
2. **Salting** (`covid#0..#N`) — лечит **и чтения, и записи**, но стоит структуры: надо знать N на ключ и scatter-read/merge по N шардам. Тяжелее, усложняет чтения. Применять только к нескольким самым горячим ключам, не глобально.
3. **Cache** (LFU) — первая линия: большинство горячих чтений вообще не доходит до БД. Для самых горячих keyword можно сделать кэш source-of-truth для top-K, а БД отдаёт холодный хвост — тогда потолок партиции уходит с критического пути.
4. **Request coalescing / single-flight** — схлопнуть конкурентные промахи по одному ключу в одно обращение к бэкенду. Дёшево, убивает thundering-herd при истечении кэша.
5. **Tiered / local cache** — app-level кэш на каждой ноде перед общим кэшем, чтобы самые горячие ключи отдавались из памяти до любого сетевого хопа.
6. **Write batching / aggregation** — ты уже делаешь это для лайков через Kinesis; это митигация горячих **записей** (схлопнуть много лайков в одно периодическое обновление). Назвать явно рядом с salting.

Первые три — заголовочные, остальное — «и вот как ещё дожать».

**Почему salting помогает записям, а replica нет:** при single-leader каждая реплика берёт каждую запись, поэтому увеличение RF не добавляет write-пропускной способности. Salting размазывает write-нагрузку по N шардам. Размен: salting меняет write-проблему на read-fan-out (теперь каждое чтение scatter-read по N шардам + merge).

## 6. Resharding ≠ фикс горячего ключа

Resharding перераспределяет ключи между нодами, но **один горячий ключ всё равно мапится на одну ноду**. Добавление ноды помогает, когда нагрузка размазана по многим ключам, и не делает ничего для одного «раскалённого» ключа. Ключ атомарен для кольца (hash ring). → resharding нужен для масштабирования по памяти, а не для hot-key.

Для одного горячего ключа единственные рычаги: **replicas (чтения)** и **salting (и то, и другое)**.

## 7. Переход к Cassandra (вместо Dynamo)

Логика: если весь SK-огород нужен только чтобы обойти лимиты Dynamo — выкинуть Dynamo, взять Cassandra. И это сильный выбор, лучше Dynamo здесь.

- **Та же идея PK/SK** → partition key + clustering key (clustering = `postId`/timestamp даёт отсортированный posting list).
- **Cassandra leaderless / multi-replica** → горячие чтения размазываются по репликам нативно — то, что Dynamo заставляет добывать вручную.
- Append-heavy, редко обновляемые posting lists — её sweet spot.

**SSTable-инсайт (твой, и он по делу):** posting list — это append-mostly, отсортированный, почти неизменный список id. Это **и есть SSTable**. Cassandra под капотом — LSM/SSTables, так что ты не хакаешь её, а используешь как задумано. Распознать «моя структура данных — уже SSTable» = правильный инстинкт. Из этого следствие: **свою реализацию SSTable писать не надо** — получаешь append-friendly, sorted-immutable-segment поведение как родной формат движка.

**S3 — коррекция:** S3 годится для **холодного хвоста**, но не для горячего пути:
- нет in-place append (надо переписывать весь объект),
- латентность per-request — десятки мс.

Новые посты аппендятся в posting lists постоянно, так что «редко обновляется» неточно — оно **редко мутирует, но часто аппендится**. Рабочий паттерн: горячие/свежие списки в Cassandra (или в кэше), холодные posting lists стареют в S3 как immutable-сегменты. **S3 = архивный tier, не serving tier.** (S3 по сути — файловое хранилище, как жёсткий диск.)

## 8. Leaderless и consistency: R, W, N, quorum

**Leaderless** = ни одна реплика не «владеет» ключом. У Dynamo (и классических primary-replica) у партиции один лидер, через который идут все записи и по умолчанию чтения — он и есть бутылочное горло (один горячий ключ = один горячий лидер). У Cassandra N реплик ключа — равноправные пиры, любая может обслужить чтение. Нет назначенного владельца → не на ком концентрироваться.

**Как Cassandra размазывает чтения (в 2 предложениях):** координатор маршрутизирует каждое чтение на одну (или R) из N реплик ключа и может выбирать **разную реплику каждый раз**, так что конкурентные чтения одного горячего ключа попадают на разные ноды.

**R / W / N и quorum (тут была серия уточнений):**
- `R` — это **не число реплик**, а сколько из них ты **ждёшь на чтении**. `R=1` означает, что данные всё равно лежат на всех N репликах; ты просто принимаешь ответ от первой ответившей.
- **Quorum** — это не «механизм чтения с реплик», а одно конкретное значение R/W: `R = большинство (N/2 + 1)`. У Cassandra есть буквальный consistency level `QUORUM`. Можно ставить R ниже или выше.
- **Размазывание чтений работает при любом R** — оно идёт от выбора реплик координатором, а не от quorum. Более высокий R **вредит** размазыванию, а не помогает.

**Главное про свежесть (твоя поправка, верная):** quorum на чтении сам по себе **ничего не гарантирует**. Гарантию «чтение видит последнюю запись» даёт соотношение **R + W > N** (overlap чтения и записи). Пример: `W=1, N=10` → чтобы быть уверенным, нужен `R=10`; большинство `R=6` легко промахивается мимо единственной ноды, взявшей запись. R в одиночку для свежести бессмысленен — важен overlap с W.

**Терминология, к которой пришли:**
- `R + W > N` — это **strong / strict consistency** (свойство, которое получаешь при достаточном overlap). Использовать `QUORUM` и для чтений, и для записей — обычный способ его достичь (большинство + большинство всегда пересекаются), но дело в overlap, а не в слове «quorum».
- Cassandra **tunable**: можно ставить R и W ниже порога (`R=1, W=1`) — это **eventual consistency**, и поэтому Cassandra «не quorum по умолчанию». Quorum-уровень — это то, во что ты опционально входишь, когда он нужен.

**Вывод по теме:** Cassandra решает горячие чтения тем, что разрешено читать с любой реплики (ценой возможного устаревшего значения — для поиска это ок). Размазывание чтений и сильная консистентность — в противоречии, выбираешь одно. **Caveat: leaderless лечит горячие чтения, а не горячие записи** — write-hot ключ всё равно бьёт по всем своим репликам (каждая реплика берёт каждую запись), так что для записей снова salting, независимо от Cassandra vs Dynamo. Твой кейс read-heavy → read-spreading Cassandra — ровно тот рычаг, что нужен.

## 9. Как реплики Cassandra сходятся (convergence)

Не один механизм, а три:
- **Read repair** — на чтении, затрагивающем несколько реплик, если координатор видит устаревшие копии, он пушит последнее значение. Работает только для ключей, которые реально читают.
- **Hinted handoff** — если реплика была недоступна во время записи, другая нода хранит «hint» и проигрывает его, когда реплика вернётся.
- **Anti-entropy repair** — плановая фоновая полная сверка (сравнение **Merkle-деревьев**), catch-all для всего, что пропустили первые два.

→ Сходимость **read-driven + плановая**: read repair бесплатно обрабатывает горячие ключи, фоновый repair гарантирует, что холодные рано или поздно синхронизируются.

**LSM/SSTable как приятное следствие:** Cassandra — LSM-дерево, пишет SSTables под капотом. Не реализуешь сам — получаешь append-friendly sorted-immutable-сегменты как родной формат.

### Разбор отказов (твой «невезучий узел»)

- Реплика **up** во время записи → получает запись напрямую.
- Реплика **down** во время записи → покрыта hint'ом, проигрывается при возврате. Но у hint'ов есть пределы: они **истекают через окно (по умолчанию ~3h)**, и если нода-координатор, держащая hint, тоже умрёт — hint потерян. Hinted handoff — **best-effort, не гарантия**.
- Hint истёк / потерян / нода лежала слишком долго → спасает только **read repair** (если этот ключ случайно прочитают) или **плановый anti-entropy (Merkle)**.

→ Если запись пропущена, hint не выжил, и **никто этот ключ не читает** — anti-entropy repair единственное, что сделает ноду консистентной. Поэтому операторы Cassandra гоняют scheduled repair как рутину: бэкстоп для холодных ключей, до которых read repair не дотягивается, а hints не покрыли.

## 10. Hinted handoff: детали (важная серия уточнений)

**Hint пишется только когда реплика была недоступна, на happy path hint'а нет.** Координатор шлёт запись всем 3 репликам параллельно; реплики 1 и 2 ack'нули, реплика 3 недоступна — только тогда координатор хранит hint для реплики 3. Если все три up — все три просто берут запись, hint'а нигде нет.

→ Hint — это **запись-исключение** («реплика 3 пропустила это, должок»), а не лог каждой записи. Записи a, b, c при здоровой реплике 3 → ноль hint'ов. Реплика 3 лежит на a, b, c → три hint'а в очереди.

**Нюанс:** реплика 3 не обязана быть полностью down — если она просто медленная и не ack'нула в таймаут, координатор может выписать ей hint, даже если запись в итоге дойдёт (источник изредка избыточных hint'ов, сверяются позже).

**`W` не меняет hint-логику.** `W` — про **acks, а не про то, скольким репликам слать**. Координатор **всегда** шлёт запись всем N=3. `W=2` означает лишь, что клиенту отвечают «success» после 2 ack'ов — слать третьей это не мешает.
- Реплика 3 здорова → всё равно получает a, b, c (просто, может, чуть позже, и её ack приходит после того, как клиент уже получил success). Hint'а нет — данные у неё есть.
- Реплика 3 down → координатор хранит hints для a, b, c, проигрывает при возврате.

> `W` = сколько ack'ов я жду (рычаг латентности/durability). Hints = что происходит с репликой, которая запись не получила (failure path). Все N всегда получают попытку записи независимо от W. `W=2` vs `W=3` меняет только, блокируешься ли на третьей.

**Валидное состояние системы:** при `W=2, R=2, N=3`, если реплика 3 медленная — её ack'и не успели, координатор удовлетворён 1+2 и **никогда не флагнул 3 как down → hints не выписаны**. Реплика 3 реально пропустила a, b, c, и система это считает нормой (W=2 выполнено).
- Сходимость для реплики 3 идёт от **read repair** + **anti-entropy (Merkle)**. Hinted handoff тут **нет** — hints существуют только когда координатор решил, что реплика отказала, а здесь он так не решил.
- При этом `R+W = 4 > N = 3` (overlap держится) означает, что каждое успешное чтение всё равно видит последнюю запись: `R=2` гарантирует, что затронешь хотя бы одну из двух up-to-date реплик, даже пока реплика 3 устаревшая. Устаревание есть, но чтения его обходят. Гарантия делает свою работу.

## 11. Параллельные записи: слать всем N, ack'ать на W

**Вопрос:** при `N=10, W=6` — не мудрее ли слать рандомным 6 (и добивать ещё 1/2/3, если ack'ов не хватило), чем слать всем 10 и довольствоваться 6 ack'ами?

**Ответ: слать всем 10 — осознанный выбор, не лень.**

Зачем остальные 4 записи: они — то, как остальные реплики остаются актуальными. Если писать только 6, оставшиеся 4 устаревшие **by design на каждую запись** — ты создаёшь перманентный бэклог, который read-repair и anti-entropy вынуждены постоянно разгребать. Плюс падает durability: данные на 6 нодах вместо 10. **W — рычаг латентности** (когда сказать клиенту «готово»), и не надо, чтобы он подменял собой replication-factor (сколько копий существует).

Send-to-all даёт бесплатно:
- **Tail-latency hedging** — нужно 6 ack'ов; выстрелив во все 10, побеждают 6 самых быстрых. Если бы слал ровно 6 и один — медленная/мёртвая нода, ты бы блокировался на отстающем, прежде чем вообще попробовать другую. Over-sending = способ обойти медленный хвост.
- **Нет round-trip «выбрать другую»** — твой fallback (попробовать 6, потом ещё, если мало) добавляет последовательный retry на критический путь. Это строго медленнее, чем parallel-fire-all-take-first-6.

**Паттерн в таких системах (Cassandra, Dynamo-style):** слать всем N параллельно, ack'ать клиента на W, остальные доезжают асинхронно.

**Синтез (твоя формулировка, точная):**
- Параллельная отправка = стоимость **одной** записи, не десяти. Wall-clock = ответ 6-й-по-скорости реплики, не сумма. Платишь латентность одной записи (+чуть-чуть), чтобы затронуть все 10. Поэтому over-sending почти бесплатен — это ~1× времени с лучшими шансами.
- Смерть >4 из 10 редка, и `W=6` — ставка против этого. `W=6/N=10` переживает 4 одновременно лежащие реплики и всё равно ack'ает. Вероятность потерять 5+ сразу (независимые отказы) крошечная. Когда не набирается 6 — запись падает **громко**, а не молча недореплицируется (правильное поведение).
- Parallel-send превращает «проблему доступности» (часть нод медленные/down) в «просто возьми первые W», и **W — это циферблат, сколько отказов проезжаешь прозрачно**. Быстрый путь и устойчивость к отказам выпадают из одного механизма.

## Сводка ключевых чисел и «строчек для интервью»

- **400KB** — лимит item в Dynamo (→ модель PK/SK, а не blob).
- **~3000 RCU** — потолок на партицию в Dynamo (→ hot partition).
- **2 log N** — стоимость обновления структуры, упорядоченной по мутирующему значению.
- **R + W > N** — strong consistency; ниже порога (R=1, W=1) — eventual.
- **~3h** — дефолтное окно жизни hint'а (hinted handoff = best-effort).
- **covid#0, covid#1, …** — salting синтетических PK для самых горячих ключей.

Сквозные тезисы:
- SK даёт **порядок внутри партиции**, не распределение; скаттерит только **salting PK**.
- **resharding ≠ hot-key fix** — ключ атомарен для кольца.
- Для горячего ключа: replica (чтения) + salting (и то, и другое) + cache (первая линия).
- Cassandra: leaderless лечит горячие **чтения**, не записи; posting list = SSTable; S3 только для холодного хвоста.
- W — рычаг латентности, а не replication-factor; слать всем N, ack на W.
- Ограниченный результат (нескроллящийся за ~1K) снимает худшую ловушку term-partitioning.
